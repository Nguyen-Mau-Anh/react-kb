# Production — 05. Internationalization: next-intl 3 vs react-i18next 15, ICU MessageFormat, RTL

> **What / Why / How** — pick **`next-intl@3`** for Next.js 14 App Router. Use **ICU MessageFormat**, never string concatenation. Plan RTL from day one with logical CSS properties and Tailwind's `dir`-aware utilities.

---

## 1. The Real Choices in 2026

| Library | npm | Best for | Status |
|---------|-----|----------|--------|
| **next-intl 3** | `next-intl@3.21` | Next.js 14/15 App Router (default 2026 pick) | Active, App-Router-native |
| **react-i18next 15** | `react-i18next@15`, `i18next@23.16`, `i18next-browser-languagedetector@8` | Vite, CRA, React Native, Pages Router | Active, framework-agnostic |
| **next-i18next 15** | `next-i18next@15` | Next.js **Pages Router** only | Maintenance — don't use for App Router |
| **FormatJS / `react-intl@7`** | `react-intl@7` | Strong ICU MessageFormat fans, Format.js ecosystem | Active |
| **`@lingui/react@4`** | `@lingui/react@4`, `@lingui/macro@4` | Compile-time message extraction, performance focus | Active |
| **Crowdin / Lokalise / Phrase** | translation management platforms | Translator workflow, not the runtime | Pair with any of the above |
| **`@formatjs/intl-localematcher@0.5`** | smaller helpers | Locale negotiation when rolling your own | Used by next-intl internally |

**The 2026 default for any new Next.js 14+ App Router project: `next-intl@3.21`.** It's the only mature library built specifically around App Router conventions (Server Components, `await`-able messages, middleware-based locale routing). Picking `react-i18next` on App Router today means fighting the framework on every route.

For React + Vite or Pages Router or React Native: `react-i18next@15` is still the most-used choice with the largest plugin ecosystem.

## 2. The "How Many Languages" Decision

| Scenario | Tool / approach |
|----------|-----------------|
| English-only with maybe one extra language for marketing | Skip a library; use a typed messages object + React Context |
| 2–10 languages, professional SaaS | `next-intl@3` (App Router) or `react-i18next@15` (everything else) |
| 10+ languages with translator workflow | next-intl/react-i18next + Crowdin or Lokalise for translator UI + git sync |
| Heavy ICU formatting (plurals, gender, dates) | `react-intl@7` (FormatJS) or next-intl (which uses FormatJS internally) |
| Strong type-safety on message keys | `@lingui/macro@4` with codegen, or next-intl + `next-intl/types` |

The rest of this document focuses on the two real picks: **next-intl 3** for Next.js, and **react-i18next 15** for everything else.

## 3. ICU MessageFormat — The Standard, Use It

The most underused i18n feature in real codebases. **ICU MessageFormat** is a string syntax for handling pluralization, gender, dates, and numbers without manual code branches:

```
{count, plural,
  =0 {No tasks}
  one {# task}
  other {# tasks}
}
```

- `count` is the variable.
- `plural` is the format type.
- `=0`, `one`, `other` are CLDR plural categories.
- `#` is the value.

This single string covers English, French, Russian (where plural rules go up to "few", "many", "other"), Polish, Welsh — every language gets the right form automatically. **No `${count} task${count === 1 ? '' : 's'}` ever again.**

### What ICU covers

```
plural    → 0/1/few/many/other (CLDR rules, varies by language)
selectordinal → "1st", "2nd", "3rd"
select    → arbitrary keys (e.g., gender)
number    → currency, percent, compact
date      → short/medium/long/full
time      → same
```

A real-world message:

```
Hello {name}, you have {count, plural,
  =0 {no new messages}
  one {# new message from {sender}}
  other {# new messages from {sender}}
}.
```

Both `next-intl@3` and `react-i18next@15` (with `i18next-icu` adapter) speak ICU natively. Use it.

### Why string concatenation is wrong

```tsx
// ❌ Concatenated strings — un-translatable
<p>You have {count} {count === 1 ? 'task' : 'tasks'}</p>

// ❌ Translated strings stitched in code — order is fixed
const msg = t('youHave') + ' ' + count + ' ' + t('tasks');
// In Japanese: "タスクが{count}個あります" — words come in different order
```

ICU strings are **single units of translation** — translators see the whole sentence and reorder freely.

## 4. next-intl 3 — Full Setup for Next.js 14 App Router

### Install

```bash
npm i next-intl@3.21
```

### Define your locales and messages

```
messages/
├── en.json
├── es.json
├── fr.json
└── ja.json
```

```json
// messages/en.json
{
  "Home": {
    "title": "Welcome",
    "greeting": "Hi, {name}!",
    "tasks": "{count, plural, =0 {No tasks} one {# task} other {# tasks}}"
  },
  "Nav": {
    "home": "Home",
    "settings": "Settings"
  }
}
```

```json
// messages/es.json
{
  "Home": {
    "title": "Bienvenido",
    "greeting": "¡Hola, {name}!",
    "tasks": "{count, plural, =0 {Sin tareas} one {# tarea} other {# tareas}}"
  },
  "Nav": { "home": "Inicio", "settings": "Configuración" }
}
```

### `i18n.ts` — central config

```ts
// i18n.ts
import { getRequestConfig } from 'next-intl/server';
import { notFound } from 'next/navigation';

export const locales = ['en', 'es', 'fr', 'ja'] as const;
export type Locale = (typeof locales)[number];
export const defaultLocale: Locale = 'en';

export default getRequestConfig(async ({ locale }) => {
  if (!locales.includes(locale as Locale)) notFound();
  return { messages: (await import(`./messages/${locale}.json`)).default };
});
```

### Middleware for locale detection + routing

```ts
// middleware.ts
import createMiddleware from 'next-intl/middleware';
import { locales, defaultLocale } from './i18n';

export default createMiddleware({
  locales,
  defaultLocale,
  localePrefix: 'as-needed',  // / for default; /es for non-default
  // 'always' → /en, /es always; 'never' → no prefix, locale via cookie
});

export const config = {
  matcher: ['/((?!_next|api|.*\\..*).*)'],
};
```

`localePrefix: 'as-needed'` is the modern best practice — clean URLs for the default language, prefixed URLs for others. Used by Vercel docs, Linear marketing, Notion's localized pages.

### `app/[locale]/layout.tsx` — locale-aware layout

```tsx
// app/[locale]/layout.tsx
import { NextIntlClientProvider } from 'next-intl';
import { getMessages, setRequestLocale } from 'next-intl/server';
import { notFound } from 'next/navigation';
import { locales } from '@/i18n';

export function generateStaticParams() {
  return locales.map((locale) => ({ locale }));
}

export default async function LocaleLayout({
  children,
  params: { locale },
}: {
  children: React.ReactNode;
  params: { locale: string };
}) {
  if (!locales.includes(locale as any)) notFound();
  setRequestLocale(locale); // enables static rendering of nested pages
  const messages = await getMessages();

  return (
    <html lang={locale} dir={locale === 'ar' || locale === 'he' ? 'rtl' : 'ltr'}>
      <body>
        <NextIntlClientProvider messages={messages}>
          {children}
        </NextIntlClientProvider>
      </body>
    </html>
  );
}
```

### Reading messages — Server Components

```tsx
// app/[locale]/page.tsx
import { useTranslations } from 'next-intl';

export default function HomePage() {
  const t = useTranslations('Home');
  return (
    <main>
      <h1>{t('title')}</h1>
      <p>{t('greeting', { name: 'Anh' })}</p>
      <p>{t('tasks', { count: 5 })}</p>
    </main>
  );
}
```

`useTranslations` works in **both** Server and Client Components — `next-intl` handles the runtime split automatically. The Server Component renders to HTML; the Client Component receives the same messages via `<NextIntlClientProvider>`.

### Reading messages — async server-side

For places where you can't use a hook (`generateMetadata`, route handlers):

```ts
import { getTranslations } from 'next-intl/server';

export async function generateMetadata({ params: { locale } }: { params: { locale: string } }) {
  const t = await getTranslations({ locale, namespace: 'Home' });
  return { title: t('title') };
}
```

### Linking — locale-aware `<Link>`

```tsx
// navigation.ts
import { createSharedPathnamesNavigation } from 'next-intl/navigation';
import { locales } from './i18n';

export const { Link, redirect, usePathname, useRouter } = createSharedPathnamesNavigation({ locales });
```

```tsx
import { Link } from '@/navigation';

<Link href="/dashboard">Dashboard</Link>
// Resolves to /dashboard for default locale, /es/dashboard for Spanish, etc.
```

This is the killer feature — you write `<Link href="/dashboard">` and `next-intl` rewrites the URL based on the active locale. **No hand-built locale-prefix logic.**

### Switching languages

```tsx
'use client';
import { usePathname, useRouter } from '@/navigation';
import { useLocale } from 'next-intl';
import { locales } from '@/i18n';

export function LanguageSwitcher() {
  const locale = useLocale();
  const pathname = usePathname();
  const router = useRouter();

  return (
    <select value={locale} onChange={(e) => router.replace(pathname, { locale: e.target.value })}>
      {locales.map((l) => <option key={l} value={l}>{l}</option>)}
    </select>
  );
}
```

The same `pathname` is preserved across locales — switching from `/es/blog/intro` to English produces `/blog/intro`, not the home page.

## 5. react-i18next 15 — For Vite, CRA, Pages Router, Native

### Install

```bash
npm i react-i18next@15 i18next@23.16 i18next-browser-languagedetector@8
# Optional ICU support:
npm i i18next-icu@2.3
```

### Setup

```ts
// i18n.ts
import i18n from 'i18next';
import { initReactI18next } from 'react-i18next';
import LanguageDetector from 'i18next-browser-languagedetector';
import ICU from 'i18next-icu';

import en from './locales/en.json';
import es from './locales/es.json';

i18n
  .use(ICU)
  .use(LanguageDetector)
  .use(initReactI18next)
  .init({
    resources: { en: { translation: en }, es: { translation: es } },
    fallbackLng: 'en',
    interpolation: { escapeValue: false },
  });

export default i18n;
```

### Use

```tsx
'use client';
import { useTranslation } from 'react-i18next';

export function HomePage() {
  const { t, i18n } = useTranslation();
  return (
    <>
      <h1>{t('home.title')}</h1>
      <p>{t('home.greeting', { name: 'Anh' })}</p>
      <p>{t('home.tasks', { count: 5 })}</p>
      <button onClick={() => i18n.changeLanguage('es')}>ES</button>
    </>
  );
}
```

### Why react-i18next still wins for Vite / Native

- **Framework-agnostic.** Same library on web, mobile (RN), and desktop (Electron).
- **Plugin ecosystem.** `i18next-http-backend@3` for lazy-loading translations, `i18next-pseudo@2` for fake-translations testing.
- **Hot reload.** Translators editing JSON sees updates without restart in Vite.
- **Massive plugin catalog.** ~50 official + many hundreds of community.

### Why react-i18next loses on Next.js 14 App Router

- **No first-class Server Components support.** You end up adding `'use client'` to every translated component, defeating the App Router's Server-default model.
- **No locale-aware `<Link>`.** Hand-build URL prefixes.
- **Hydration mismatches** when client detects a different locale than the server rendered. You spend 2 hours debugging timezones.

For App Router: use **next-intl**. For Pages Router or non-Next.js: **react-i18next**.

## 6. Translation Workflow — Real Production Patterns

### Source language vs translated languages

The convention: **`en.json` is the source of truth, edited by developers**. Other languages (`es.json`, `ja.json`) are translated copies. Translators don't edit JSON directly; they use a TMS (Translation Management System).

### TMS choices in 2026

| Tool | Best for | Pricing |
|------|----------|---------|
| **Crowdin** | Open-source projects, free for OSS | $10–149/mo (free for OSS) |
| **Lokalise** | Developer-oriented, strong CLI + API + git sync | $120+/mo |
| **Phrase** | Enterprise, granular permissions | $30+/mo |
| **Tolgee** | Self-hosted, modern dev experience | Free (self-host) or hosted |
| **Localizely** | Smaller teams, simple pricing | $26–149/mo |

The standard workflow:
1. Developer edits `en.json` → commits.
2. CI runs `crowdin upload` (or equivalent) → translators see new keys in the TMS.
3. Translators edit in the TMS UI.
4. CI runs `crowdin download` daily → opens a PR with updated `es.json`, `ja.json`, etc.
5. PR is merged → deploy → users see translations.

`tolgee@5` (`@tolgee/react@5`) deserves a callout: it provides an in-page translator UI where the translator literally clicks text on your live site to edit it. Cuts the translator round-trip dramatically.

### Type-safe message keys

```bash
npm i -D @next-intl/types  # next-intl
```

For next-intl, generate `messages.d.ts` from `en.json`:

```ts
// global.d.ts
type Messages = typeof import('./messages/en.json');
declare interface IntlMessages extends Messages {}
```

Now `t('Home.title')` autocompletes; `t('Home.tnotreal')` is a TypeScript error. **Catch missing keys at build, not in production.**

For react-i18next, the equivalent is the `i18next.d.ts` declaration:

```ts
// i18next.d.ts
import 'i18next';
import en from './locales/en.json';

declare module 'i18next' {
  interface CustomTypeOptions {
    defaultNS: 'translation';
    resources: { translation: typeof en };
  }
}
```

## 7. Number, Date, Currency Formatting

Use the **Intl.* APIs** built into the browser. No library needed for the hard part.

```tsx
import { useFormatter, useNow } from 'next-intl';

export function PriceTag({ amount, currency }: { amount: number; currency: string }) {
  const format = useFormatter();
  return <span>{format.number(amount, { style: 'currency', currency })}</span>;
  // → $1,234.56 in en-US
  // → 1.234,56 € in de-DE
  // → ¥1,235 in ja-JP
}

export function RelativeTime({ date }: { date: Date }) {
  const format = useFormatter();
  const now = useNow();
  return <span>{format.relativeTime(date, now)}</span>;
  // → "3 days ago" in en
  // → "hace 3 días" in es
}
```

`useFormatter` wraps `Intl.NumberFormat`, `Intl.DateTimeFormat`, and `Intl.RelativeTimeFormat` with locale awareness. **Don't roll your own currency formatting.**

For react-i18next, the same APIs work — just call `Intl.NumberFormat(i18n.language, ...)` directly.

## 8. RTL — Arabic, Hebrew, Persian

### What changes in RTL

- Text reads right-to-left.
- Layout mirrors: navbar, sidebars, lists.
- Icons that imply direction (arrows, chevrons) flip.
- Numbers stay LTR (mostly — Arabic-Indic digits are an exception).

### CSS — use logical properties

The single biggest RTL win is **CSS logical properties**. Stop writing `margin-left`, start writing `margin-inline-start`:

```css
/* ❌ LTR-only */
.card { margin-left: 1rem; padding-right: 0.5rem; }

/* ✅ Direction-agnostic */
.card { margin-inline-start: 1rem; padding-inline-end: 0.5rem; }
```

In RTL, `margin-inline-start` automatically becomes the right margin. **No JS, no checks, no per-locale CSS.**

### Tailwind 3.4 — RTL utilities built in

```tsx
<div dir="rtl">
  <div className="ms-4 me-2 ps-3 pe-1">
    {/* margin-inline-start, margin-inline-end, padding-inline-start, padding-inline-end */}
  </div>
</div>
```

`ms-*`, `me-*`, `ps-*`, `pe-*` (and `start-*`/`end-*` for `left`/`right` properties) flip automatically based on the `dir` attribute on a parent.

For text alignment: `text-start` and `text-end` instead of `text-left` and `text-right`.

### Setting `dir` on `<html>`

```tsx
<html lang={locale} dir={isRtlLocale(locale) ? 'rtl' : 'ltr'}>
```

```ts
const RTL_LOCALES = new Set(['ar', 'he', 'fa', 'ur']);
const isRtlLocale = (locale: string) => RTL_LOCALES.has(locale.split('-')[0]);
```

### Icons that should flip

```tsx
// Arrow that means "next" should point left in RTL:
<ChevronRight className="rtl:scale-x-[-1]" />
```

Tailwind 3.4 ships an `rtl:` variant — works because the parent `<html dir="rtl">` is set. Same for `ltr:` if you need direction-specific overrides.

### Real RTL testing checklist

- [ ] Set `dir="rtl"` and visually scan every page.
- [ ] Check that arrows / chevrons flip.
- [ ] Verify modals open from the correct side.
- [ ] Confirm form labels align correctly.
- [ ] Test bi-directional input (Hebrew with English brand names mixed in).
- [ ] Check that `Intl.NumberFormat` uses Arabic-Indic numerals if the locale calls for it (`ar-SA` does, `ar-EG` does, but configurable).

## 9. SEO — Hreflang and Localized Metadata

### Hreflang via Metadata API

```tsx
// app/[locale]/page.tsx
import { getTranslations } from 'next-intl/server';
import { locales } from '@/i18n';

export async function generateMetadata({ params: { locale } }: { params: { locale: string } }) {
  const t = await getTranslations({ locale, namespace: 'Home' });
  const path = '/'; // current path
  return {
    title: t('title'),
    alternates: {
      canonical: `https://example.com${locale === 'en' ? '' : `/${locale}`}${path}`,
      languages: Object.fromEntries(
        locales.map((l) => [l, `https://example.com${l === 'en' ? '' : `/${l}`}${path}`])
      ),
    },
  };
}
```

Google reads `<link rel="alternate" hreflang="...">` to know which language version to show in which country's search results. **This is the difference between French SEO traffic and zero French SEO traffic.**

Covered in `07.nextjs/07-seo-metadata.md`.

### Sitemaps per locale

```ts
// app/sitemap.ts
import type { MetadataRoute } from 'next';
import { locales } from '@/i18n';

export default function sitemap(): MetadataRoute.Sitemap {
  const routes = ['', '/about', '/pricing'];
  return routes.flatMap((path) =>
    locales.map((locale) => ({
      url: `https://example.com${locale === 'en' ? '' : `/${locale}`}${path}`,
      alternates: {
        languages: Object.fromEntries(
          locales.map((l) => [l, `https://example.com${l === 'en' ? '' : `/${l}`}${path}`])
        ),
      },
    }))
  );
}
```

## 10. Date / Number Locale Edge Cases

| Edge case | Reality | Handling |
|-----------|---------|----------|
| **Plural rules differ wildly** | English has 2 forms; Russian has 4; Arabic has 6 | ICU MessageFormat plurals — never hand-code |
| **First day of week** | US: Sunday; EU: Monday; Arab states: Saturday | `Intl.DateTimeFormat(locale, { weekday: 'long' })` + locale-aware calendar libs (`date-fns/locale@3`) |
| **Decimal separator** | US: `1,234.56`; Germany: `1.234,56`; France: `1 234,56` | `Intl.NumberFormat` handles it |
| **Currency placement** | `$1.50` (US) vs `1,50 €` (DE) vs `¥1.5` (JP) | `Intl.NumberFormat({ style: 'currency' })` |
| **Time zone** | User in Tokyo viewing a US-server-rendered page | Always convert on the client OR pass UTC ISO strings; `Intl.DateTimeFormat({ timeZone: 'Asia/Tokyo' })` |
| **Calendar systems** | Gregorian (default), Buddhist (Thailand), Japanese era (`reiwa`), Hijri (Saudi Arabia) | `Intl.DateTimeFormat(locale, { calendar: 'islamic' })` |
| **Bi-directional text** | Hebrew with embedded English | Use `<bdi>` or LTR/RTL marks (`‫`, `‬`) only when needed |
| **Fonts that lack glyphs** | A custom font might not have Arabic or Japanese | Subset fonts per locale or use `font-display: swap` + system-font fallbacks |

## 11. Lazy-Loading Translations

Don't ship every language's JSON to every user. Two real patterns:

### Pattern A — next-intl: dynamic import per locale (default)

The `i18n.ts` shown in §4 already does this — `await import(\`./messages/${locale}.json\`)` only loads the active locale. Each locale ends up in its own chunk.

### Pattern B — react-i18next: HTTP backend

```bash
npm i i18next-http-backend@3
```

```ts
i18n
  .use(HttpBackend)
  .init({
    backend: { loadPath: '/locales/{{lng}}.json' },
  });
```

Translations are fetched at runtime per locale. Combine with `i18next-resources-to-backend@1` for a hybrid (bundled defaults + remote overrides).

## 12. Translator Workflow — Pseudo-Localization for Testing

`i18next-pseudo@2` (or write your own ~30 lines for next-intl) generates a fake locale where every English string becomes `[!!! Wȩłçömé!!!]`. Catches:

- Strings that aren't wrapped in `t()` (they stay English).
- UI that breaks on 30%-longer text (German, French often run +30%).
- RTL bugs when you also flip direction.

Real teams ship pseudo-localization to staging environments and let QA file bugs against it.

## 13. Common Pitfalls

| Pitfall | Fix |
|---------|-----|
| Hydration mismatch on locale-dependent text | Always set `<html lang={locale}>` server-side; use `useNow()` for "X minutes ago" instead of `new Date()` directly |
| `t('Home.title')` returns the key, not the string | Namespace mismatch (`useTranslations('Home')` vs `t('title')`) or missing key in JSON |
| Concatenating translated parts produces wrong word order | Use ICU MessageFormat for the whole sentence |
| `Intl.NumberFormat` returns "NaN" | You passed a string; coerce to `Number(value)` |
| RTL layout breaks on flexbox | Use `flex-row-reverse` aware logical properties or set `dir` on the flex container |
| Date "yesterday" vs "1 day ago" inconsistency | Use `format.relativeTime(date, now)` from next-intl, not custom "X days ago" math |
| Translations not updating after JSON edit | Restart the dev server or wire up `i18next` HMR |
| Locale switch doesn't persist | Set a cookie (`NEXT_LOCALE`) — next-intl middleware handles this with `localePrefix: 'never'` |
| All translations download even on SSR | Confirm dynamic import in `i18n.ts`; check Network tab for per-locale chunks |
| Static export breaks with dynamic locales | Set `generateStaticParams` to enumerate every `[locale]` |
| Right-aligned input fields in RTL show cursor wrong | This is correct RTL behavior; don't override |
| Long German strings break the navbar | Shorten translations or design for 30% longer copy |
